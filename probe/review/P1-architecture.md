# Architecture & Design Review

## Critical

- **[critical] `resolvers/Resolvers.kt:112-129`** — `resolveAny()` does not actually race: `coroutineScope` waits for all children to complete before returning, and `cancel()` cannot abort in-flight blocking OkHttp `execute()` calls. The loop at line 121-127 also does not break early after a winner is found — it still receives all `jobs.size` messages. Net result: wall-clock time = `max(candidates)`, not `min(candidates)`. The comment "losers are cancelled mid-flight" is cosmetic; a hanging locker (30s TCP timeout) still blocks every episode resolution for 30s regardless of the winner. Impact: the advertised concurrency win over a sequential walk is largely illusory for slow-but-alive locker hosts, directly degrading the user experience on sites that embed multiple lockers.

- **[critical] `resolvers/LockerRegistry.kt:159-198`** — `resolveCandidates()` is **dead code**: no production caller in the entire app invokes it. The "works on first contact" claim for unknown hosts (the entire reason the evidence-based classifier exists) is unreachable at runtime. Instead, providers hand-roll their own resolution (NaijaVault's `resolveAny` sweep, NaijaPrey's `extractFileLink`), and the unknown-host probe path (1KB validator, HostHealth learning) is never exercised. Impact: the app does not actually "probe unknown hosts once via StreamValidator" in production — unknown lockers are only resolved if the 25-resolver flat list happens to claim them, and if no resolver claims them, NaijaVault resolves to the raw HTML page URL. The central architectural promise of the evidence-based design is unfulfilled.

- **[critical] `data/net/HttpClient.kt:79`, `resolvers/Resolvers.kt:86-89,183-193,196-200`** — `HttpClient.lastFailure` is a single `@Volatile` mutable field shared across all concurrent requests. `resolveAny()` launches up to 3 concurrent `resolve()` calls, each of which reads `lastFailure` to decide retry behavior and records health verdicts. Because `lastFailure` is overwritten on every response, a 429 from locker B can be attributed to locker A's failure, and `isNetworkClassFailure()`'s `before` capture reads stale shared state. Impact: the health ledger and retry logic produce corrupted decisions under concurrent resolution — a 429-poisoned host may be thrown into backoff, and network-class retries mis-fire across concurrent candidates.

## Major

- **[major] `providers/NaijaVaultProvider.kt:221-227`** — `resolveEpisode` returns the raw episode page URL as `directUrl` when resolution fails (`val finalUrl = direct ?: episodeUrl`). The project's own code (NaijaPreyProvider line 145) explicitly warns `"NEVER return the raw page URL as directUrl — that 'downloads' the HTML page itself"`. The engine's `StreamValidator` preflight will catch the HTML page and fail with `ValidationFailed`, but every episode with a dead link creates a doomed task that the user must manually cancel. This is a direct inconsistency with the project's own architecture rule.

- **[major] `resolvers/LockerRegistry.kt:183`** — `resolveCandidates()` probes unknown hosts with `StreamValidator.validate(u, emptyMap())` — **no headers at all**. `StreamValidator`'s own docstring (line 24-28) says the caller must pass "the EXACT headers the real download will send (referer policies matter: vidbasic 403s with a Referer, megaplay CDNs 403 without theirs)". Many CDNs require a specific `Referer` or `Origin` header; probing with empty headers will produce 403 responses, causing the probe to return a rejection reason, `recordFail()` to be called, and the unknown host to be skipped. Impact: the "works on first contact" mechanism fails for any referer-gated CDN, even though the real download would work. (Note: this code is dead per the critical finding above, but if wired in, it would be broken.)

- **[major] `resolvers/LockerRegistry.kt:74`** — The OTA locker host list **replaces** the built-in defaults, not unions with them: `DynamicRulesManager.getLockerHosts().ifEmpty { DEFAULT_LOCKER_HOSTS }`. If the OTA playbook sets `lockerHosts` to a list that omits entries like `"dood."`, `"swish"`, or `"waffi"`, those hosts silently lose their known-locker status and are demoted to `Unknown`. Since `isKnownMedia()` also gates NaijaVault's episode-list union (`knownElsewhere` filter, line 102), episodes on those hosts silently drop from curated lists. The OTA data is signed, but the semantics are subtractive — a playbook author who adds a new locker host without re-listing the old ones causes a regression. No tests or CI checks enforce union semantics.

- **[major] `resolvers/LockerRegistry.kt:30-37,75-76`** — Approximately 7 of 25 `DEFAULT_LOCKER_HOSTS` entries are hostname fragments that **never match** the classifier's hostname-boundary logic: `"dood."`, `"waffi"`, `"filevault"`, `"wildshare"`, `"gtoddl"`, `"wapkizfile"`, `"swish"`. The match condition `host == kh || host.endsWith(".$kh")` requires a full hostname boundary — `host.endsWith(".dood.")` is never true for a real host like `"dood.re"`, and `host == "dood."` is never true either. These entries are dead weight in the default list, giving a false sense of coverage. Known hosts like `dood.re`, `waffi.cloud`, `wildshare.net`, `filevault.com.ng` are classified `Unknown` rather than `Locker`, bypassing the concurrent racing path and NaijaVault's curated union.

- **[major] `resolvers/LockerRegistry.kt:183-186`, `pipeline/StreamValidator.kt:74-90`** — The unknown-host probe's `sniff()` validator only rejects HTML, JSON, PK (archive), and MZ (executable) headers. Any binary blob that is not one of these — a PNG image, a WOFF2 font, a JavaScript file, a 0-byte response — passes the probe and causes `HostHealth.recordOk(host)`. The host is then permanently promoted to "proven locker" via `hasProvenLocker(host)` (threshold: `ok >= 1`), with no decay. Impact: a single probe pass permanently marks a non-locker host as a known locker, poisoning the classifier's learning model for the lifetime of the app install. The evidence model trades precision for recall more aggressively than the docstring acknowledges.

- **[major] `pipeline/PipelineError.kt:15-64`** — The 8-subtype sealed `PipelineError` hierarchy is almost entirely decorative. Of the 8 subtypes, only `ValidationFailed` is ever thrown (in DownloadEngine line 1362), and `BudgetExceeded.message` is extracted for a journal line (Resolvers.kt:136). Every resolver and provider catches all exceptions with `catch (_: Exception) {}` and returns `null` or empty `ShowDetails`. The `classify()` companion function (line 55-63) is never called. The project's stated rule "every stage fails LOUDLY" does not match the code — the pipeline fails silently with nulls, and the rich error taxonomy exists only in the sealed class definition.

## Minor

- **[minor] `resolvers/Resolvers.kt:158-167`** — `resolveInternal` can cache an intermediate gateway page URL as the final result. When a resolver returns a non-media URL and the deeper recursion returns null, `return direct` (line 167) hands back the intermediate page. The depth-0 caller then caches this URL in `ResolveCache` and calls `HostHealth.recordOk` for the gateway host. For the cache TTL (default 10 min), the engine receives the gateway page URL as the "resolved stream", the engine's `StreamValidator` rejects it as HTML, and the task fails. Every retry within the TTL re-serves the same cached garbage. Impact: a transient resolver failure produces a 10-minute window of guaranteed failures for that episode.

- **[minor] `resolvers/Resolvers.kt:32-58`** — The 25-resolver flat list has overlapping `canResolve` claims with positional coupling. `GenericLockerResolver` (index 25) claims `vikingfile.com` and `lulacloud.com`, but `VikingFileResolver` (index 8) and `LulaCloudResolver` (index 9) claim the same hosts with different logic. `StreamwishResolver` (index 19) includes `"filelions."` in its host list, and `VidhideResolver` (index 21) also includes `"filelions."`. Ordering determines which resolver runs first, and a new resolver must be carefully placed before `GenericLockerResolver` to win. The pattern scales linearly but the overlap makes it fragile — a positional misplacement can silently change resolution behavior.

- **[minor] `resolvers/LockerRegistry.kt:134-138`** — `findLockerLinksInHtml()` parses HTML with `Jsoup.parse(html)` (no base URI). When `a.attr("abs:href")` is called without a base URI, Jsoup returns `""` for relative URLs. The fallback chain then reads `a.attr("href")` — the raw relative URL — which `classify()` receives. Since `classify()` extracts the host via `URI(clean).host`, a relative URL like `/download/123` has no host and returns `MediaKind.None`. Relative locker links are silently dropped. The regex fallback (line 143) also only matches absolute `https?://` prefixes. Impact: sites that serve locker links as relative URLs lose all their locker candidates through the extraction pipeline.

- **[minor] `pipeline/HostHealth.kt:140-146`** — `persist()` writes JSON to disk on **every** `recordOk()` and `recordFail()` call. On a page with 10 locker candidates, this means up to 10 disk writes per resolution attempt. The `take(500)` limit iterates `ConcurrentHashMap.entries` in nondeterministic order, not "hottest entries" as claimed. Impact: unnecessary disk I/O on the resolution hot path; the 500-entry cap may evict the most recently active host if the iterator happens to skip it.

- **[minor] `data/rules/DynamicRulesManager.kt:255-276`** — The `decryptRules()` legacy path accepts unsigned AES-CBC payloads (when the incoming text does not start with `{`). The AES key and IV are hardcoded in the APK (line 49-50). The ECDSA P-256 signature is only enforced for v2 envelope payloads. A MITM who has extracted the APK's AES key can forge an unsigned payload that bypasses the signature entirely. The project's threat model acknowledges this ("obfuscation-grade, NOT strong security"), but the signature's presence in the architecture documentation implies protection that the legacy path does not provide.

- **[minor] `providers/NaijaVaultProvider.kt:211-213`** — `resolveEpisode` hardcodes a locker host regex `(?:streamsss|streamwish|streamtape|doodstream|dood\\.|...)` that duplicates host lists already maintained in `LockerRegistry.DEFAULT_LOCKER_HOSTS`, `DynamicRulesManager`, and each resolver's `HOSTS`. When a new locker host is added to the resolution chain, three places must be updated, and the provider's regex is an easy miss. This is a module-boundary violation: the provider should use `LockerRegistry.findLockerLinksInHtml()` or `DynamicRulesManager.getLockerHosts()` instead of maintaining its own copy.

## Nits

- **[nit] `resolvers/LockerRegistry.kt:74`** — `DynamicRulesManager.getLockerHosts()` already returns `emptyList()` when empty (DynamicRulesManager.kt:204-205), so the `.ifEmpty { DEFAULT_LOCKER_HOSTS }` is correct but the receiver function's own `ifEmpty` is redundant.

- **[nit] `resolvers/LockerRegistry.kt:41`** — `NAV_SEGMENTS` includes `"movie-download"` and `"download-movies"`, but the `navWord` check at line 100 uses `s.contains("movies")` which catches all `"movies"` substrings — the specific entries are redundant. The `"movies"` check is also broad enough to match `"moviesarea"` or `"moviestreams"` (both plausible real locker path segments on unknown hosts), but this is a design trade-off acknowledged in the comment.

- **[nit] `pipeline/HostHealth.kt:130-131`** — `hasProvenLocker` uses `ok >= 1` with no decay mechanism. A host that succeeded once months ago remains a "proven locker" forever. This is a design choice but means the learning model has no forgetting function — if a host changes behavior, the classifier won't adapt.

- **[nit] `providers/NaijaVaultProvider.kt:102-103`** — The `knownElsewhere` filter calls `LockerRegistry.isKnownMedia(h)` which internally calls `classify()`. `classify()` for a URL with a known media extension returns `Direct`, which `isKnownMedia` returns true. But these are direct media links, not lockers — they should be caught by the `isDownloadLink` gate at line 129-131 rather than included in the OTA selector union. The union is documented but the semantic overlap between the two paths is confusing.

## Overall Verdict

The architecture has a critical gap: `resolveCandidates()` — the crown-jewel abstraction that was supposed to enable "works on first contact" for unknown locker hosts — is dead code with no production caller. The resolveAny race does not provide the advertised speedup because coroutineScope semantics and non-interruptible blocking HTTP turn the race into a sequential wait-for-slowest. The evidence-based learning model is undermined by a lenient probe that promotes non-media hosts to "proven locker" permanently, a shared mutable global that corrupts concurrent health verdicts, and OTA semantics that silently subtract built-in coverage. The PipelineError taxonomy is decorative, and providers routinely bypass the central abstractions (hand-rolling their own host lists and resolution loops). The kernel is thicker than claimed — DEFAULT_LOCKER_HOSTS, the 25-resolver registry, engine constants, and host-level referer policies are all hardcoded in the APK. A future maintainer adding a new site or locker would need to update the provider, the resolver list, LockerRegistry's default seeds, and DynamicRulesManager's default host policies — and the first thing they'd discover is that the central arbitration API they're told to use doesn't actually do anything at runtime.
