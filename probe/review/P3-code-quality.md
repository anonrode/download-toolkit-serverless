# Code Quality & Kotlin Idioms Review

Findings grouped by severity. Each entry identifies exact file:line and describes realistic impact for a phone-based scraper/downloader.

---

## Critical

- **[critical] `resolvers/Resolvers.kt:280,305,333,439,504,588,622,640,663,684,706,732,752,825,905,1104,1140,1185,1247,1289,1319,1347,1366,1396` + all provider files** — Every resolver and provider wraps the entire `resolve` body in `catch (_: Exception) {}`. Kotlin's `kotlinx.coroutines.CancellationException` extends `java.util.concurrent.CancellationException` which extends `IllegalStateException` which extends `RuntimeException` which extends `Exception`. Therefore **every resolver swallows coroutine cancellation**. When `resolveAny` races 3 candidates and the first wins, it calls `jobs.forEach { it.cancel() }`, but the cancelled coroutines continue executing because their `catch (_: Exception)` absorbs `CancellationException`. The real impact: blocking OkHttp `execute()` calls inside losers are NOT interrupted — they drain full responses (up to 3 MB capped body reads, 15s read timeouts) on the user's mobile data. The "losers cancelled mid-flight" optimization is largely cosmetic. Furthermore, the engine's `withTimeout(RESOLVE_TIMEOUT_MS)` cannot enforce its 90-second hard ceiling because the cancelled child swallows the exception and blocks until its HTTP calls complete naturally, potentially keeping the task in `RESOLVING` for much longer than 90s.

- **[critical] `pipeline/PipelineError.kt:1-65`** — The `PipelineError` sealed class, complete with 7 subclasses (SiteDown, HostDead, RateLimited, BlockedIp, TokenExpired, ParseEmpty, ValidationFailed, BudgetExceeded) and a `classify` factory method, is **used in only 2 places in the entire 7000+ line codebase**: once to extract `.message` from `BudgetExceeded` (`Resolvers.kt:136`), and once to throw `ValidationFailed` (`DownloadEngine.kt:1362`). `PipelineError.classify` is dead code. Every resolver, provider, and pipeline component returns `null` or empty results instead of throwing typed errors. The documentation promises "every stage fails LOUDLY with one of these" but the code delivers the opposite — silent null-surface failures. Future contributors will find the abstraction misleading: the class hierarchy suggests the system uses typed errors, but in practice everything is `String?`. The diagnostics live in `PipelineJournal` and `DebugLog` lines, which is adequate, but the sealed class is a maintenance burden and a broken promise.

- **[critical] `data/net/HttpClient.kt:79`** — `lastFailure` is a single `@Volatile var` shared across **every concurrent resolver call**. During `resolveAny`'s 3-way race, resolver A may fail with "HTTP 404" and resolver B with "timeout"; whichever writes `lastFailure` last determines what all callers see. `resolveWithRetry` captures `before = HttpClient.lastFailure` then calls `resolver.resolve()` (which may set `lastFailure` from its own call OR from another concurrent call), then compares `current = HttpClient.lastFailure` to decide network-class retry. This misattribution causes: (a) transient failures from one candidate to suppress retries for another, (b) `HostHealth.recordFail` to misattribute failures to the wrong host, and (c) the "Canceled" filter in `HostHealth.recordFail` (lines 98-101) to guard against a cancelled call's `lastFailure` bleeding into an unrelated host's health record, but the guard reads the shared mutable — another concurrent cancellation could mark a healthy host as cancelled-skipped. Impact: flaky resolution, incorrect host backoff, wasted retries on mobile data.

## Major

- **[major] 85 bare `catch (_: Exception) {}` blocks across the codebase** (see listing from `grep`). While some are legitimate (cleanup that must not fail, like `try { f.delete() } catch (_: Throwable) {}`), the bulk are in resolvers, providers, and pipeline functions where they convert every possible failure (timeout, parse error, HTTP 5xx, Jsoup selector change, JSON key miss, encryption failure, WASM extraction failure) into `null` or empty lists. The project's own audit identifies this as the root of past bugs ("silent failures, no ERROR line"). The pipeline journal (`PipelineJournal.hop`) does record many of these at the resolver-registry level, but not the internal failure before null propagation — so a Jsoup parse failure in a provider is invisible unless the provider itself logs. Real impact: a site changes its HTML slightly → parse returns null → user sees "Could not crack stream link" with no granular cause. Diagnosing requires the activity log, and even then the log doesn't show which stage inside the resolver failed.

- **[major] No unit tests for the DownloadEngine `app/src/main/java/com/anonrode/downloader/engine/DownloadEngine.kt`** — The largest file (1749 lines), containing the task queue, watchdog (stall/crawl/rate-drop/zombie detection), HLS preflight with playlist rewriting/resolution picker, progress monitoring, storage guard, network-pause logic, 3-backend fallback chain, token refresh on 403/404/410, and aria2c-to-Turbo rescue handoff. **Zero unit tests.** Any name or change to the watchdog heuristics, the stall detection floor, the rate-drop detector, or the retry chain can break without detection. In contrast, the schedulers and pipeline primitives (3 files) have adequate tests. Impact: the most complex, most failure-prone component in the app has no automated safety net.

- **[major] No unit tests for any of the 25 resolvers in `resolvers/Resolvers.kt`** — Every resolver does string surgery, regex matching, Jsoup parsing, or WASM decryption that could be unit-tested with fixture HTML. Instead, they are only verified by live-site probing (the Python verification suite). A regex change that accidentally captures the wrong URL, or a parse failure on a known fixture, won't be caught until a real site breaks. Impact: regressions go undetected until a user reports "this locker no longer works."

- **[major] `engine/DownloadEngine.kt:306` (pause) lines 306-325 and `engine/DownloadEngine.kt:339` (cancel) lines 339-365** — Both call `HttpClient.cancelInFlight()` which cancels **every in-flight non-search HTTP call across all tasks**, not just the paused/cancelled task's. The comment acknowledges this: "without these, a paused task kept draining mobile data." However, the side effect is that other tasks concurrently resolving or probing suffer HTTP call cancellations, causing their resolvers to return `null` and potentially fail those tasks with "Could not crack stream link." On a multi-task phone session, pausing one download silently sabotages another's resolution. This is a shared-mutable-state design flaw: there is no per-task request tracking beyond `tag`, and only `"search"` calls are exempt.

- **[major] Test pollution from singleton mutable state** — `DynamicRulesManager`, `HostHealth`, `ResolveCache`, and `PipelineJournal` are all Kotlin `object` singletons. Tests in `DynamicRulesManagerTest`, `PipelineTest`, and `LockerRegistryTest` call `DynamicRulesManager.parseRulesJson()` and `HostHealth.recordFail/recordOk` without resetting state between tests. For example: `DynamicRulesManagerTest.parseRulesJson_applies...` sets `tokenTtlMinutes = 15` — this affects `ResolveCache` TTL in any test run after it. `PipelineTest.hostHealth_backoffWindowAfterFailures_resetsOnSuccess` records 3 fails on `healthtest.example` — if `LockerRegistryTest` runs after and happens to reuse that host, `hasProvenLocker` or `isUsable` would see stale data. Test order matters; concurrent execution would be incorrect. Impact: fragile CI, false positives/negatives depending on test order.

- **[major] `providers/AnitakuProvider.kt:229-233`** — When resolution fails entirely, `resolveEpisode` returns `episodeUrl` (the raw page URL) as `directUrl`. The engine's `accept()` in `resolveStreamUrl` rejects it (because `directUrl == permUrl`), but any direct caller that trusts the recipe would feed an HTML page to the downloader. This is a ticking footgun: a refactor of the engine's accept logic could let this through, producing a corrupted "download" of an HTML page. The NaijaPreyProvider explicitly avoids this (comment at line 144), but Anitaku doesn't.

## Minor

- **[minor] `pipeline/StreamValidator.sniff` and `engine/DownloadEngine.looksLikeHtml` duplicate HTML detection logic** — `looksLikeHtml` (`DownloadEngine.kt:372-394`) and `sniff` (`StreamValidator.kt:74-90`) both check for `<!doctype html>`, `<html`, `<head`, `<body`, etc. on the first bytes. However, `looksLikeHtml` also checks `{` (JSON objects) while `sniff` does not, and `sniff` checks `PK`/`MZ` headers which `looksLikeHtml` doesn't. The duplication makes it possible to fix one but forget the other. Real impact: minor maintenance burden; no known current divergence.

- **[minor] `resolvers/Resolvers.kt:136`** — `PipelineError.BudgetExceeded("depth", 0).message ?: "depth limit"` constructs a typed exception solely to extract its `.message` string. This is a code smell: the exception is never thrown, never caught, never classified. It's used as a poor man's format string.

- **[minor] `engine/DownloadEngine.kt:701,713,728`** — `resolveStreamUrl` wraps `ProviderRegistry.resolveEpisode` and per-provider `resolveEpisode` calls in `try { ... } catch (_: Exception) {}`. This swallows provider-specific errors (e.g., `SecurityException` from torrent shield, `IllegalStateException` from missing aria2c binary) that should propagate. While the engine's fallback logic continues, the error is invisible in the pipeline journal (no `hop` recorded for the provider failure).

- **[minor] `engine/DownloadEngine.kt:504-509`** — `isStreamingLink` hardcodes `kickassanime` as an M3U8 indicator. This is a site-specific shortcut in a function that should be generic. If the provider is updated or renamed, this remains. Minor: currently works.

- **[minor] `engine/DownloadEngine.kt:478-491`** — `sanitizeComponent` manually replaces HTML entities (`&amp;`, `&#8211;`, etc.) instead of using `org.jsoup.Jsoup.parse(raw).text()` or Android's `Html.fromHtml()`. This misses many HTML entities (e.g., `&lt;`, `&gt;`, `&hellip;`). Impact: rare edge cases where scraped titles contain HTML entities beyond the listed set produce filenames with literal `&amp;` or `&#...;` text.

- **[minor] `data/models/Models.kt:64`** — `etaSeconds` is declared in `DownloadTask` but the engine's progress watchdog always passes `eta = 0L` (line 1180). The yt-dlp backend does parse an ETA from the progress line (`eta` from `YoutubeDL.execute` callback, line 276), which IS passed through to `onProgress` (line 305) and saved to `updateProgress` (line 1551). But the Turbo path and the filesystem-progress path never provide ETA. So `etaSeconds` is populated only for yt-dlp downloads, and is always 0 for Turbo/aria2c downloads. The UI (`DownloadsScreen.kt:350`) shows it when non-zero. Real impact: no ETA for multi-socket Turbo downloads.

- **[minor] `engine/DownloadEngine.kt:263-279`** — The deduplicate-loop in `enqueue` calls `repository.snapshot().any { it.filePath == ... }` for each task, and for duplicates increments a counter and retries. With `downloadAllEpisodes` (40 episodes), this is O(n^2) on the snapshot list per enqueue call, and the snapshot is a full list copy. Real impact: a batch enqueue of 100+ episodes could be noticably slow on low-end phones, but this is a rare operation.

- **[minor] `viewmodel/MainViewModel.kt:140-186`** — The search function properly deduplicates identical queries and uses `cancelTagged("search")` to kill stale HTTP calls. However, the `searchSequence` mechanic uses `finally { if (seq == searchSequence) ... }`. If searchJob is cancelled and a new search starts before the old job's finally runs, both finally blocks execute (the old one sees seq != searchSequence and skips), but this relies on `searchSequence` being written before `searchJob = viewModelScope.launch { ... }`. In single-threaded Compose dispatch this holds, but it's a subtle timing assumption.

## Nits

- **[nit] `engine/DownloadEngine.kt:41-43`** — `downloadTorrentsWifiOnly` is a property alias for `wifiOnlyTorrents` with an explicit getter/setter. This is dead code: it exists solely because the Settingsheet reads `engine.downloadTorrentsWiFiOnly` while the engine uses `wifiOnlyTorrents` internally. The aliasing is confusing for a future contributor — they may add logic to one but not the other.

- **[nit] `resolvers/Resolvers.kt:921` (`LoadedfilesResolver.lastWorkingHost`) and `Resolvers.kt:1207` (`VidhideResolver.lastWorkingHost`)** — `@Volatile` mutable host caches on resolver singletons. They are written and read from resolver coroutines, and while `@Volatile` makes the memory visibility correct, there is no synchronization around read-then-write sequences (e.g., `lastWorkingHost = effective.substringAfter(...)` in the Loadedfiles host-answer loop), so two concurrent episodes resolving the same host can interleave. In practice the outcome is identical hosts, so impact is nil — but it's the kind of shared mutable state that a contributor could extend unsafely.

- **[nit] `resolvers/Resolvers.kt:112`** — `Channel.UNLIMITED` used in `resolveAny`. Since only `jobs.size` sends are made, this is bounded, but `UNLIMITED` signals that any coroutine can send without backpressure. Fine.

## Verdict

The codebase reads like a battle-tested live-operations notebook: the comments are exceptional, the observed-failure-driven logic is honest, and the test suite for the pure pipeline primitives (aria2c control-file parsing, Turbo pause/resume, shield layers, rules crypto) is genuinely good. But the core of the app — the 1749-line `DownloadEngine` state machine and all 25 resolvers — has zero automated coverage, and the blanket `catch (_: Exception)` pattern (85 sites) swallows coroutine cancellation, which silently defeats the resolver racing, the 90s resolve timeout, and the pause/cancel paths. The `PipelineError` sealed hierarchy is dead weight that misleads future contributors, and shared globals (`HttpClient.lastFailure`, `cancelInFlight`) leak state across concurrent tasks so that pausing one download can sabotage another. For a single-developer app this is a solid 7/10 on readability and a 4/10 on testability of the riskiest code; the highest-leverage improvements are a `CancellationException`-safe exception policy in resolvers, per-task HTTP call tracking, and a first round of `DownloadEngine` unit tests around the watchdog and queue.

- **[nit] `engine/YoutubeDlDownloader.kt:347`** — `throw InterruptedException("Task was cancelled...")` from a coroutine. `InterruptedException` is a `Thread`-interruption construct, not a coroutine-cancellation one; the rest of the codebase correctly uses `kotlinx.coroutines.CancellationException`. It happens to compile (suspend functions may throw any `Exception`) but a future contributor reading the retry loop will not understand why a thread-interruption exception is being thrown from a coroutine. Also, the preceding `catch (_: InterruptedException) { throw InterruptedException(...) }` at line 346-348 is a no-op rethrow — it converts a non-existent condition into the same exception.

- **[nit] `util/DebugLog.kt:35-36`** — `SimpleDateFormat` instances are shared class-level fields; `timeFormat` is used from the single writer thread plus `crashLog()` which runs on whatever thread the crash handler invoked it from. SimpleDateFormat is not thread-safe; a crash landing while the writer thread formats a line can corrupt output. Low risk (rare race), but a one-line fix with `ThreadLocal` or `DateTimeFormatter` would remove it.
