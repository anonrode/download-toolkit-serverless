# Maintainability & OTA Data-Driven Design Review

## Critical

- **[critical] `DynamicRulesManager.kt:307-495`** `parseRulesJson` mutates global state incrementally and non-transactionally. Every section (`domains`, `mirrors`, `sites`, `hostPolicies`, `lockerHosts`, `knownDead`, `tokenTtlMinutes`, …) is applied to the shared `activeDomains`/`activeHostPolicies`/etc. lists as it parses. The single `try/catch` at line 492-494 returns `false` on ANY exception — and the `syncFromGitHub` caller (line 228-230) treats `false` as "keeping bundled defaults". But the defaults were already half-overwritten. Concretely: `dynamicList.getJSONObject(i)` at line 474 throws `JSONException` if any `dynamic_providers` entry is a string instead of an object (a malformed-but-schema-passing payload — `encrypt_rules.py` does NOT validate `dynamic_providers`), so a playbook with `"dynamic_providers": ["x"]` applies new domains/mirrors/hostPolicies/lockerHosts and THEN fails, leaving the app running on a half-applied playbook that it reports as "failed to parse". There is no snapshot, no rollback, no version compare, and no way to recover except re-sync. The claimed fallback is broken.

- **[critical] `DynamicRulesManager.kt:255-281` + `encrypt_rules.py:253-264`** The ECDSA "authenticity" guarantee has a downgrade hole. `decryptRules` only verifies the signature when the envelope is v2 OR carries a sig (`isV2 || sigB64.isNotBlank()`, line 263-264). A v1 envelope with no `sig` field skips verification entirely and is decrypted with the envelope's own IV. The maintainer tooling actively produces such payloads: `encrypt_rules.py:260-264` emits an **unsigned v1 envelope with only a warning** when no signing key is found ("app accepts it until enforcement flips" — no enforcement flip exists). Any repo hijacker (the exact threat model the HANDOVER cites: "A repo hijack or CDN MITM can no longer feed users fake rules", HANDOVER.md:104 / DynamicRulesManager.kt:56-57) can push a self-encrypted v1 envelope — the AES key ships in the APK — and every app on earth will accept it as legacy. The signature system protects only against tampering with v2 envelopes, which is a weak subset of the claimed protection. I verified the current `.enc` is a valid v2 signed envelope, so this is latent, not exploited — but the "serverless signed OTA" security claim is materially overstated.

## Major

- **[major] `LockerRegistry.kt:30-37, 74` + `scraper_rules.json:286-310`** The locker-host list exists in THREE copies that replace rather than merge: Kotlin `DEFAULT_LOCKER_HOSTS` (25 entries), Python `DEFAULT_LOCKER_HOSTS` mirror in `conformance.py:48-55` (25 entries, matches Kotlin), and the playbook's `lockerHosts` (23 entries). `getLockerHosts().ifEmpty { DEFAULT_LOCKER_HOSTS }` means a non-empty playbook list **replaces** the built-in defaults entirely. The current playbook drops `"dood."`, `"hglink.tv"`, and `"swish"` that the built-ins contain (and adds `vdl.np-downloader.com`). After any successful sync, URLs on dood.wf/dood.re classify as `Unknown` instead of `Locker` — they still work via first-contact probing, so the breakage is silent performance drift, but a future playbook edit that forgets a host silently degrades every install. Three sources of truth with no test asserting they match (see test drift below).

- **[major] `conformance.py:442-517` vs `SearchStrategyRunner.kt:79-83`** The Python mirror's `urlTemplate` nav-junk guard has DIVERGED from the Kotlin app: conformance requires `path.count("/") >= 2` (line 497), while the app only rejects paths with `<= 1` slash AND no media markers (`-drama`, `-episode-`, `season`, `-movie-`). `/vincenzo-korean-drama/` (0 slashes, contains "-drama") is ACCEPTED by the Kotlin app and REJECTED by the conformance mirror. The mirror's own docstring (line 449) even claims "requires >=3 path segments, same guard as the app" — the comment, the code, and the app disagree with each other. Any site whose real show pages are single-segment drama slugs will fail conformance's strategy chain while working in the app — or worse, pass while the app breaks, depending on direction of drift. This is exactly the "two classification implementations in two languages" tax, realized.

- **[major] `conformance.py:353-378`** Stage 1 (`stage_search`) uses the weak heuristic `len(cards) > 0 or len(links) > 5` — a dead search endpoint returning a 200 with 6 navigation anchors PASSES. The project already learned this lesson (lines 185-187: "counting 'page returned 200 with content' as a hit scores fake shows 15/15") but only fixed it in the optional `--search-quality` mode; the default stage sweep still uses the weak check. Combined with `conformance.yml:7-20` (manual dispatch only, `strict` defaults to false, failures "do not gate anything"), the conformance suite is an advisory report: site decay ships to users with a green-adjacent scorecard.

- **[major] `conformance.yml:1-20` + `ota-rules.yml:39-58`** CI gates nothing. `ota-rules.yml` validates only signature + schema of whatever `.enc` happens to be committed; `conformance.yml` is manual-only and non-blocking. Nothing in CI runs the Kotlin code, the resolver algorithms, the watchdog, or the engine. The regression classes that actually bit this project — the DramaRain/Nkiri/Rocks classify-gate reverts (HANDOVER.md:113-121), the `.webmanifest`-vs-`.webm` regex bug in `NaijaPreyProvider.kt:169`, the wildshare re-route (`NaijaPreyProvider.kt:135-140`), the HLS 0-byte stalls — are all invisible to conformance because they live in Kotlin provider/resolver code the runner never executes. A new maintainer who trusts "all jobs green" after a conformance run gets no protection for the app's actual failure modes.

- **[major] `encrypt_rules.py:93-173`** Schema validation has meaningful gaps. Unvalidated fields: `searchStrategies` (no type whitelist — `"type": "foobar"` passes and silently no-ops in both runner implementations), `knownDead` (no type/length check), `lockerHosts` (no check), `dynamic_providers` (no check — the exact field whose malformed content triggers the partial-application bug above), `urlTemplates`, `directMediaExtensions`, `tokenTtlMinutes` (app coerces 1..240, CI doesn't check), and `minAppVersion` — which is allow-listed at line 170 but **never read by DynamicRulesManager**, so a payload declaring `minAppVersion: 99` applies to an APK that lacks the features it requires. Any of these can ship past CI and degrade or half-break the app.

- **[major] `DynamicRulesManager.kt:307-495`** Playbook fields are additive-only: nothing ever removes a key absent from the new payload. `activeDomains` keeps domains from older playbooks forever; `activeMirrors` likewise; `activeLockerHosts` is cleared before re-fill (line 441-442), but `domains`, `mirrors`, `sites`, `hostPolicies` (cleared, 405-406), `searchStrategies` (cleared 455-456) — inconsistent clearing. A revoked domain or retired mirror stays active indefinitely. Stale state accumulates across syncs with no version-rollback path.

- **[major] `NaijaVaultProvider.kt:210-217, 226` + `NaijaPreyProvider.kt:151`** Core resolution logic is hardcoded in Kotlin, not data: the locker-host regex in NaijaVault's `resolveEpisode` fallback (line 211) hardcodes a 13-host alternation that duplicates (and can drift from) `lockerHosts`/`DEFAULT_LOCKER_HOSTS`; both providers hardcode `parallelSockets = 16` in their `DownloadRecipe` (NaijaVault.kt:226, NaijaPrey.kt:151), silently overriding the user's "Aria2c Parallel Sockets" setting in the UI. The engine's constants (watchdog floors, stall defaults, HLS fragment count) are all Kotlin. The "OTA reduces APK updates" claim holds for domains/mirrors/referers/search strategies — the 10-commit v3.0.3 stack (HANDOVER.md:38-51) was however almost entirely Kotlin changes: compile fixes (f44405f), test fixes (e95d76b), storage permission flow (9311851), NaijaVault selector union (019dc0e), the naijaprey wildshare chain fix (24ce28d). Only c3893a4 (lockerHosts seeding) and the searchStrategies commits were pure data. Realistic ratio: roughly 1 in 8 recent fixes was OTA-able.

## Minor

- **[minor] `conformance.py:366-367`** Stage-2 "episodes" validates the playbook's `episodeSelector` — but only `NaijaVaultProvider.kt:96-107` actually reads `episodeSelector` in the Kotlin app. The playbook declares selectors for pluto, 9jarocks, naijaprey, asianc, dramarain (scraper_rules.json:151-201) that NO Kotlin provider consumes; the conformance suite validates a field the app mostly ignores, while the real per-provider episode extraction (RocksProvider RSS, DramaRain gates, NaijaPrey nav filters) is never tested. Conformance green ≠ app drawers work.

- **[minor] `HANDOVER_AUDIT.md:83-91, 138-163`** HANDOVER_AUDIT.md is stale to the point of contradicting both the code and HANDOVER.md: it claims `DownloadService` holds a "high-performance WifiLock" (the actual `DownloadService.kt` acquires only a PARTIAL_WAKE_LOCK; no WifiLock exists anywhere), claims "8+ resolvers" (HANDOVER.md says 25), and asserts "Zero commits and zero pushes made" while the repo has 10+ pushed commits and tag v3.0.3. Nothing in HANDOVER.md warns the new maintainer that the audit doc is outdated. A new maintainer reading both gets contradictory architecture claims (e.g. chasing a nonexistent WifiLock).

- **[minor] `DynamicRulesManager.kt:449`** `tokenTtlMinutes` is coerced to 1..240, but `encrypt_rules.py` doesn't validate it — the app's coercion is the only guard, and a 1-minute TTL would make every resolver token expire within a single HLS download, forcing repeated re-resolution. No doc mentions the interplay.

- **[minor] `HANDOVER.md:95-100`** The signing keypair lives in a single local folder (`C:\Users\Anon\anon-serverless-app-maintenance-build\`) with no documented backup. If that machine dies, the recovery path — regenerate keypair, update GitHub secret, update `OTA_PUB_B64` in encrypt_rules.py AND `rulesSigningPubB64` in DynamicRulesManager.kt, and **ship a new APK with the new public key** — is an APK release. The bootstrapping public key cannot be rotated via OTA, so a lost private key forces exactly the kind of release the OTA system was built to avoid. The doc covers the steps; the single-point-of-failure risk itself is undiscussed.

- **[minor] `scripts/encrypt_rules.py:253-264`** On a fresh machine without the key folder (the documented default path), running the documented command (`python scripts/encrypt_rules.py`, HANDOVER.md checklist item 9) silently writes an UNSIGNED v1 envelope to the repo with only a console warning. Combined with the v1 acceptance in `decryptRules`, a maintainer following the docs on a new laptop ships an unsigned, unverifiable payload that the app accepts as legacy. The workflow ota-rules.yml would then fail on push (verify_envelope refuses unsigned), which is the only backstop — and it runs after the commit lands.

- **[minor] `ota-rules.yml:16-22`** The workflow triggers on pushes touching `scraper_rules.json.enc` — but not on pushes touching `scripts/encrypt_rules.py`… actually it does (path list includes both). However there is NO trigger on `probe/conformance.py` or `probe/` changes, and no scheduled run, so mirror drift (see the urlTemplate divergence above) can live for months without anyone running the suite.

- **[minor] `conformance.py:70-107`** `classify_media` mirrors `LockerRegistry.classify` by hand. The "20/20 parity verified" claim (HANDOVER.md:109) is a one-time manual statement, not an automated cross-check — the conformance container can't run the Kotlin code, and there is no shared fixture asserting both implementations agree. Every future change to nav-junk semantics, extension lists, or the `-drama` slug rule must be hand-mirrored in Kotlin, Python, AND the JVM tests, with no tool enforcing it. This is the single highest ongoing-maintenance cost in the project.

- **[minor] `HANDOVER.md:53-56`** The handover candidly documents the two CI bugs that the no-local-toolchain workflow produced (LockerRegistry never compiled until first push; stale test threshold). This is honest and useful, but it means "everything on master is pushed" is only as true as the last CI run — the project has shipped code that had NEVER compiled. For a maintainer, the lesson should be a pre-push compile gate (e.g. a draft PR), not just a "watch gh run" habit.

## Nits

- **[nit] `LockerRegistryTest.kt:109-116`** `lockerHosts_otaParsed` calls `DynamicRulesManager.parseRulesJson` and permanently mutates the singleton's global state (`activeLockerHosts = ["myhost.example", "other.example"]`). No test resets state afterward. JUnit 4's default method order is unspecified and JVM-dependent, so if this test runs before `classify_knownLockerHosts` (line 28-38) or `findLockerLinks_extractsHrefsAndSkipsNavJunk` (line 83-97), those tests FAIL — `getLockerHosts()` returns the non-empty OTA list, `streamsss.net` is no longer a known locker, and classify returns `None`. The suite is order-dependent flaky-by-construction; `DynamicRulesManager` needs a test reset hook.

- **[nit] `DynamicRulesManager.kt:51`** `RULES_IV_HEX` is a fixed default IV ("5b7e9d...") shared with the legacy format, and the v2 envelope overrides it — fine — but the constant's presence invites a maintainer to reuse it in a new envelope builder, recreating the fixed-IV weakness encrypt_rules.py explicitly upgraded away from (docstring lines 18-19).

- **[nit] `scraper_rules.json:280-284`** `knownDead` is populated with domain fragments ("jisooido.top", "jiminido"), and `isKnownDead` uses substring `contains` matching — "jiminido" also matches "jiminido.evil.example". Substring matching on host fragments is already how the rest of the system works (hostPolicies), but for a denylist it is the risky direction: a dead host fragment can silently kill a live host that contains the fragment.

- **[nit] `conformance.py:496`** `full_url.replace(base, "")` replaces the base string ANYWHERE in the URL, not just the prefix — a base like "dramarain.com" appearing in a query parameter corrupts the path-depth computation. Works today because bases are hosts; fragile.

- **[nit] `.gitignore` and the plaintext/encrypted pair** — I verified the committed `scraper_rules.json.enc` decrypts to exactly the current `scraper_rules.json` (same version 2026.08.23.1), so the pair IS in sync today. But the plaintext is gitignored by design (`.gitignore:29`), so there is no automated check that the committed `.enc` matches the current plaintext; the 4-hour timestamp gap between the two files shows how easily a stale `.enc` can ship after a plaintext edit.

---

## Verdict

The OTA playbook genuinely reduces APK-update frequency for the narrow class of changes it was designed for — domain mirrors, referer policies, search strategies, locker-host seeds — and the v2 signed envelope plus schema caps are a solid foundation. But the claim is over-extended: the recent history is ~1 OTA fix for every 8 Kotlin fixes (wildshare re-routing, selector unions, engine constants, the compile-time crash), the payload parser can half-apply a malformed playbook with no rollback, and the unsigned-v1 acceptance path quietly nullifies the "repo hijack" security claim the project advertises. The conformance suite is a genuinely useful live-canary, but it tests a Python re-implementation of the app's logic — it has already diverged from the Kotlin (urlTemplate guard) and cannot catch the regressions that actually broke this app (classify-gate reverts, webmanifest regex, HLS stalls). The documentation is unusually honest and current in HANDOVER.md, but HANDOVER_AUDIT.md contradicts it (phantom WifiLock, "zero commits"), and the single-local-folder signing key means the OTA system's own bootstrapping key cannot be rotated without an APK release. A new maintainer can keep this system alive, but only if they treat the playbook as one layer among several Kotlin-bound layers, run conformance as an advisory check, and never trust the two classification implementations to stay in sync on their own.
