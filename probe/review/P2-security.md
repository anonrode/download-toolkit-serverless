# Security Review — Anon Downloader (serverless scraper/downloader)

Scope: OTA playbook pipeline, permissions, network layer, secrets scan, torrent shield, share intents, certificate handling. All findings verified against the code at the listed paths.

## Critical

- **[critical] `app/src/main/java/com/anonrode/downloader/data/rules/DynamicRulesManager.kt:263-272`** — The ECDSA signature is NOT enforced for legacy/v1 envelopes. `val isV2 = env.optInt("v", 1) >= 2` then `if (isV2 || sigB64.isNotBlank())` — verification only runs when the payload *claims* to be v2 or *carries* a sig. Any attacker who can write the repo (the exact "repo hijack" threat the design claims to stop, per `DynamicRulesManager.kt:56-57` and `scripts/encrypt_rules.py:17-19`) simply pushes `{"v":1,"iv":...,"payload":<base64>}` with no `sig` field, and every install accepts it. The AES key needed to craft that payload is public (committed in `scripts/encrypt_rules.py:43`). The legacy fixed-IV raw-base64 format is likewise accepted unconditionally (`DynamicRulesManager.kt:275-277`), and a plaintext JSON cache is accepted too (`DynamicRulesManager.kt:144` `decryptRules(raw) ?: raw`). The signing script itself admits the app "accepts it until enforcement flips" (`scripts/encrypt_rules.py:261-263`) — enforcement never flipped on-device. Realistic impact: a compromised maintainer account or repo takeover can serve arbitrary scraping rules (domains, mirrors, selectors, host policies, dynamic providers) to every install, redirecting all scrape/download traffic to attacker-controlled hosts and driving users to malicious download pages; the claimed integrity property is defeated exactly where it is claimed to hold. The CI gate in `ota-rules.yml:47` only validates the committed file and is advisory — it runs after the same account that would push the malicious payload.

- **[critical] `scripts/encrypt_rules.py:43` + git history** — The AES confidentiality layer is decorative, defeating the stated purpose of the encryption ("site owners watching the repo must not read the selectors", `ota-rules.yml:6`). The AES key `8f3a9c21d4e65b0789a2c4f6d1e3b5a7` is committed in the same public repo as the ciphertext, and the full plaintext `scraper_rules.json` is retrievable from git history (commits `51b7b27`, `33b0c73`, `a53c513`, `5c6468b`, `86b2aa4`, `c30e577` — verified: `git show 33b0c73:scraper_rules.json` dumps the selectors and domains). Any repo watcher can decrypt the current `.enc` in seconds. The only real protection is the ECDSA signature — which, per the finding above, the app does not enforce for v1 payloads. Net: the entire "signed/encrypted OTA" framing provides neither confidentiality nor (as implemented) authenticity.

## Major

- **[major] `app/build.gradle.kts:60`** — The release APK is signed with the debug keystore: `signingConfig = signingConfigs.getByName("debug")` (comment at line 48: "Standard debug signing for release artifact distribution"). Debug keystores are the well-known Android SDK key (password `android`), and in CI a fresh random debug keystore is generated per build environment, so: (a) every CI build's APK has a *different* signing key — users cannot install one build over the previous one (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`) without uninstalling; (b) the release channel has zero authenticity — anyone can fork this public repo, build, sign with the public debug key, and publish a trojan "Anon Downloader" that is cryptographically indistinguishable from the official release; a MITM on the GitHub Release download is undetectable. For a sideloaded app whose users are told to trust the APK, the distribution root of trust is absent.

- **[major] `app/src/main/AndroidManifest.xml:16` + `app/src/main/java/com/anonrode/downloader/util/DebugLog.kt:5-16`** — `allowBackup="true"` with no `dataExtractionRules`/`fullBackupContent`, combined with an always-on activity journal that logs "literally everything — every user action and every engine/network/backend event". Concretely: pasted share text (`MainViewModel.kt:89`), every search query (`MainViewModel.kt:149`), every enqueued episode URL (`MainViewModel.kt:234`), and every HTTP request URL including full query strings — i.e. session tokens (`HttpClient.kt:208-210` logs `GET ${safeUrl(url)}` which retains `?pt=`/`?token=` parameters). Android Auto Backup uploads `filesDir` (where the daily log files live) to Google Drive. Realistic impact: the user's complete search/download history — for a scraper of pirated streaming content, legally sensitive in most jurisdictions — and token-bearing stream URLs are exfiltrated to Google's cloud, and to any app the user picks via the "Share Activity Log" feature (`SettingsSheet.kt:803-812`). Nothing in the log is redacted; the 7-day default retention (`DebugLog.kt:24`) just bounds disk, not the backup copy.

- **[major] `app/src/main/AndroidManifest.xml:22`** — `android:usesCleartextTraffic="true"` with no `networkSecurityConfig`, so cleartext is allowed for every host. The app deliberately handles `http://` locker hosts (`Resolvers.kt:1441-1443`, `isRootLockerDomain` accepts `http://downloadwella.com` / `http://wetafiles.com`) and downloads arbitrary `http://` media URLs. A network attacker (rogue Wi-Fi, ISP, compromised router) can substitute content on any http CDN link. The post-download magic-byte check (`DownloadEngine.kt:1643`, `TorrentSecurityShield.validateDownloadedFile`) catches MZ/ELF/PK/HTML decoys on the single produced file, so executable substitution is partially mitigated, but arbitrary media-content substitution, plaintext token/URL exposure, and cleartext Referer/UA headers remain. In a censorship-bypass context (the app's own DoH fallback exists to dodge Nigerian ISP DNS poisoning, `HttpClient.kt:96-106`), the ISP the user is evading is exactly the party that can tamper with these http connections.

- **[major] `app/src/main/java/com/anonrode/downloader/ui/screens/QuickShareActivity.kt:114-120`** — Magnets shared into the app bypass the pre-download TorrentSecurityShield entirely. `validateTorrent` (Layers 1-6: uploader trust, extension blacklist, negative filters, size plausibility) is only invoked on the search path (`TorrentProvider.kt:80,157`). A shared magnet goes straight to `engine.enqueue(sourceUrl = parsed.magnet)` verbatim — no infohash check, no extension screening, no `buildSanitizedMagnet` (so attacker-chosen `&tr=` trackers are honored). Post-download, Layer 7 inspects only the single `producedFile` chosen by "freshest by lastModified" (`YoutubeDlDownloader.kt:637-641`); sibling files in a multi-file torrent are never magic-checked, and when `selectIndexes` is null (no file picker) aria2c downloads ALL swarm files including blocked-extension payloads. Realistic impact: a shared magnet can deposit `.apk`/`.exe`/archive-password-scam payloads into `Download/Anon` that were never extension-filtered, and the attacker's tracker records the user's IP on first announce.

## Minor

- **[minor] `app/src/main/java/com/anonrode/downloader/data/net/HttpClient.kt:41-64`** — The shared cookie jar itself is sound: in-memory only (no disk persistence), OkHttp's `Cookie.matches()` enforces domain/path/secure scoping so cookies cannot leak across hosts, and the 400-cookie cap bounds growth. Residual issues: eviction is `removeAt(0)` (line 54), which can drop a live locker-handshake session cookie mid-chain under load; and the jar is in-memory, so every app restart starts cold — functional, not security. The more notable leak is the DoH fallback: when system DNS fails, every scraped hostname is sent to `dns.google` (`HttpClient.kt:106`) — for an app whose users are bypassing censoring ISPs, a DNS-failure is exactly when the censorship-evasive request is disclosed to Google.

- **[minor] `app/src/main/java/com/anonrode/downloader/data/rules/DynamicRulesManager.kt:185`** — Referer policy matching is bare substring matching (`low.contains(it.match)`). `match: "pluto"` fires for any host containing the substring (e.g. `pluto.evil.com`, `xplutoy.com`) and sends the fabricated `exact:https://megaplay.buzz/` referer there; `"megap."`, `"nkiri"`, `"blogger.com"` are equally over-broad. Coherence: the schema allows a `"site"` directive (`encrypt_rules.py:159`) but the app resolves it to sending *nothing* (`DynamicRulesManager.kt:190`) — a silent gap between playbook semantics and behavior. Impact: the app masquerades as traffic from megaplay.buzz to unrelated (potentially attacker-controlled) hosts, a fingerprinting and policy-coherence bug.

- **[minor] `scripts/encrypt_rules.py:16-17,52-53,228-230`** — The documented model ("private half exists ONLY as the GitHub Actions secret", echoed at `DynamicRulesManager.kt:55`) is false. CI never signs — `ota-rules.yml` only *validates*; signing happens on the maintainer's machine, where the default key path is a plaintext PEM (`~/anon-serverless-app-maintenance-build/ota_signing_private_key.pem`, `NoEncryption()` at line 230), falling back to the `OTA_SIGNING_PRIVATE_KEY` env var. The actual security boundary is an unencrypted file on a laptop, not a secret store. Key rotation: the comment at `DynamicRulesManager.kt:58` concedes rotation requires a new APK release; the AES key can only ever be changed by an APK update (both the script and the app hardcode it, and the legacy fixed-IV path uses the same constants) — so the crypto layer cannot be rotated OTA without breaking every installed client. Rotation of the signing key is "ship a release and hope the install base upgrades" — effectively not feasible as an OTA property.

- **[minor] `app/src/main/java/com/anonrode/downloader/engine/YoutubeDlDownloader.kt:592`** — aria2c runs torrent downloads with `--check-certificate=false`. Tracker and HTTPS peer connections are not TLS-verified, so a MITM can inject fake tracker responses and bogus peer lists. The real mitigation is the privacy mode (`YoutubeDlDownloader.kt:537-549`: DHT/LPD/PEX off, `--bt-require-crypto=true`, ephemeral listen ports) — which is off by default (`DownloadEngine.kt:154`). With it off, the user's IP propagates through DHT/peer gossip to the swarm — inherent to BitTorrent but worth being explicit about, since the app's own "shield" branding suggests more protection than exists.

- **[minor] `app/src/main/java/com/anonrode/downloader/resolvers/Resolvers.kt:207-208`** — Hardcoded third-party AES key/IV (`KEY = "94588293375053432799222445521289"`, `IV = "5259228356829423"`) used to decrypt a site's `data-value` payloads. This is the *site's* content key, not an app secret — it must ship in the APK by design — so it is trivially extractable and the site can rotate it at will. Not a user-facing vulnerability, but it is a hardcoded key in the repo that the secret scan flags, and it demonstrates the same "encryption is obfuscation" pattern as the OTA layer.

## Nits

- **[nit]** No TLS pinning anywhere (no `CertificatePinner`, no `network_security_config.xml`). For a normal scraper this is acceptable, but given the OTA chain's integrity is supposed to be load-bearing, the transport itself has no root of trust beyond stock CA validation — combined with the debug-signed APK and the v1 signature bypass, nothing in the chain is actually verifiable end-to-end.
- **[nit]** `app/src/main/res/xml/file_paths.xml:2` exposes `<external-path path="." />` — the FileProvider maps the entire external storage. Today it is only used for the single-file log share with `FLAG_GRANT_READ_URI_PERMISSION` (`SettingsSheet.kt:803-812`), so the grant is limited to that URI; but the mapping is broad for any future share path.
- **[nit]** `.github/workflows/build-apk.yml:9-10` grants `permissions: contents: write` to the release job; a compromised dependency in the CI build could publish malicious APKs (which are debug-signed anyway — see the major finding above).
- **[nit]** `MainActivity.kt:237-248` + `QuickShareActivity.kt:86-99`: the exported share activity with `pref_instant_social` enabled means any installed app can silently trigger downloads of arbitrary URLs/magnets with zero taps — intended feature, but it is also a vector for data/storage abuse and for associating the user's IP with attacker-chosen content.

## Areas checked with no material issues

- **Private key absence verified**: no `.pem`/`.key`/`.jks`/keystore files exist in the repo, no `BEGIN ... PRIVATE KEY` string anywhere, and no key material was ever committed to git history (the keypair was moved out in commit `ec71475`). The only secrets referenced in workflows are `secrets.GITHUB_TOKEN` (`build-apk.yml:163`) and `CONFORMANCE_PUB_B64` (`conformance.yml:40`), which is a public verification key — appropriate.
- **Cookie cross-host leakage**: none — domain scoping is enforced by OkHttp; no cookie is ever persisted to disk.
- **No WebView anywhere**: the app renders no remote content, so there is no script-execution surface from scraped pages — the injected-rule impact is limited to directing traffic, not running code.
- **Torrent path-traversal guard**: with `MANAGE_EXTERNAL_STORAGE` (justified for direct-path writes to `Download/Anon` on API 30+, but a heavy hammer that grants read access to all user files), the traversal guard (`TorrentSecurityShield.kt:326` + canonical-path check at `DownloadEngine.kt:1643`) is the only boundary between untrusted torrent paths and the user's whole storage — it exists and is correctly implemented; the gap is the shared-magnet pre-check bypass described above.
- **TorrentSecurityShield regexes**: the `\b` sequences in `TorrentSecurityShield.kt:70-73,105` are literal backslash-b (verified by octal dump), i.e. correct regex word boundaries — no broken filters.

## Overall verdict

The OTA signing pipeline is the headline feature and the headline failure: the AES layer is pure security theater (key committed, plaintext in git history), and the ECDSA signature — the one meaningful control — is bypassable on-device with a v1 envelope, so a repo hijack can still feed every install fake rules, exactly the scenario the design claims to prevent. Distribution integrity is likewise absent: release APKs are signed with the per-build debug key, so users cannot update across builds and cannot distinguish official APKs from trojans. The privacy posture is the next tier of problems: an always-on, unredacted activity log (full search/download history plus token-bearing URLs) combined with `allowBackup="true"` ships the user's entire usage history to Google Drive, and global cleartext traffic plus an unredacted DoH fallback expose a censorship-bypass app's traffic to the very network it is evading. The torrent shield's Layer 7 magic-byte inspection is genuinely useful, but the shared-magnet path bypasses Layers 1-6 entirely, so the shield's effective protection is one file's header. The app's honest strengths — no WebView, domain-scoped in-memory cookies, absent private key, working traversal guard — do not offset that the security model's central claims are, as implemented, false.
