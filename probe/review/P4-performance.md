# Performance & Resource Usage Review

Findings grouped by severity. Each entry identifies exact file:line and describes realistic impact for a phone scraping live sites and downloading on limited bandwidth.

---

## Critical

- **[critical] `engine/DownloadEngine.kt:306-325` and `engine/DownloadEngine.kt:339-365` — `pause()`/`cancel()` call `HttpClient.cancelInFlight()` which cancels every in-flight non-search HTTP call across ALL tasks.** The comment at lines 310-314 is honest about why ("a paused task kept draining mobile data") but the implementation is a sledgehammer: `HttpClient.cancelInFlight()` (`data/net/HttpClient.kt:244-257`) iterates the global `inFlightCalls` list and cancels everything except `search`-tagged calls. A phone with 2 downloads active (one resolving, one downloading) that pauses the downloading task will cancel the OTHER task's resolver chain mid-flight — that task's `getText` returns null, its resolve fails, and the user sees "Could not crack the stream link" for a healthy site. The cancellation is also not per-task: `pauseForNetwork` (line 327) and `cancel` (line 339) all call the same global nuke. The in-flight call registry should be keyed by task id like `TurboDownloader.activeCalls` (TurboDownloader.kt:47), not flat.

- **[critical] Blocking OkHttp `execute()` calls run on the shared `Dispatchers.IO` pool — 48+ threads can be pinned for hours by 3 concurrent segmented downloads.** `TurboDownloader.download` (`engine/TurboDownloader.kt:134`) wraps everything in `withContext(Dispatchers.IO)`, then each of the up-to-16 worker coroutines (line 386-397) calls `call.execute()` (line 326) — a blocking call that occupies a thread of the IO dispatcher for the entire transfer. `Dispatchers.IO` has a hard cap of 64 threads; 3 tasks × 16 sockets = 48 threads held for the full download duration (hours for a 2 GB file). Add the yt-dlp sync `execute()` (YoutubeDlDownloader.kt:276) and the resolver chains' blocking executes (HttpClient.kt:207), and there can be essentially no IO threads left for `loadEpisodes`, `repository.persist()`, the HLS estimator, or a new task's resolution while downloads run. Realistic impact on a mid-range phone: search and episode loading freeze during active downloads, and a fourth download's resolve is delayed by seconds per hop.

## Major

- **[major] `resolvers/Resolvers.kt:102-130` — the "losers cancelled mid-flight" race does not stop their in-flight HTTP requests.** When the first candidate wins, `jobs.forEach { it.cancel() }` marks the coroutines cancelled, but (a) the blocking `execute()` calls are not tied to coroutine cancellation, and (b) every resolver swallows `CancellationException` in `catch (_: Exception)`. So the losers' requests run to completion — a full page fetch each, up to the 15s read timeout — while the caller already has its answer. On a slow network, a 3-candidate race can mean 3 full page bodies (up to 3 MB each, capped at `MAX_TEXT_BYTES`) drain even after the winner is found. The per-candidate catch in `launch { try { resolve(u, quality) } catch (_: Exception) { null } ... }` also converts cancellation into a result, so the channel receiver cannot distinguish "cancelled" from "failed". To make the race actually cancel losers, requests must be registered per task/tag and cancelled like `cancelTagged` does for search.

- **[major] `engine/DownloadEngine.kt:824-860` — `preflightHls` fetches EVERY variant playlist in the master, not just the one yt-dlp will consume.** The loop over `mediaLines` (all non-tag lines) fetches each URL containing ".m3u8" (`HttpClient.get(...).use { ... cappedText(res) }`, line 830), rewrites it to a local file (line 839), and repoints the master (lines 844-848). Masters from vidsrc-family CDNs routinely list 3-8 variants, so one preflight costs N+1 playlist fetches plus the 4 segment probes and optional audio probe. Preflight can run twice per task (stale-token refresh at lines 1328-1331, yt-dlp-failure refresh at line 1598), and each refresh re-fetches the full variant set. Playlists are small (KB), so the bandwidth cost is modest — but on a slow mobile network each fetch is a round trip of seconds, and the whole preflight happens while the task sits in `RESOLVING`/`DOWNLOADING` at 0 bytes, inflating time-to-first-byte. Only the first variant is actually probed/estimated; the rest are fetched purely to be rewritten, which is only useful if yt-dlp selects them.

- **[major] `engine/DownloadEngine.kt:1339-1341` — the HLS size estimate is seeded into `totalBytes`, so an unsound estimate becomes a user-visible lie.** The comment block at lines 760-765 calls the estimate "diagnostic-only", but `if (hlsSizeEstimate[0] > 0L) repository.updateProgress(task.id, downloaded = 0L, total = hlsSizeEstimate[0], ...)` feeds it directly into the progress bar. The estimator (`engine/HlsSizeEstimator.kt:53-59`) computes mean-of-4-samples × segment count × remux factor. Four samples at fixed playlist percentiles is only sound for constant-bitrate content; VBR HLS (action scenes, black bars) can deviate by 2-3×. When the estimate overstates size, the user sees progress crawl near 0% for a long time; when it understates, progress jumps and ETA resets at completion. The estimator's own failure modes (line 89: `if (samples.any { it == null }) return null` — a single failed probe kills the whole estimate) are fine, but the fixed percentiles ignore the actual bitrate distribution. Impact: misleading progress/ETA on exactly the HLS streams this app targets.

- **[major] `providers/ProviderRegistry.kt:44-91` — search cache and episode cache are unbounded `ConcurrentHashMap`s.** `searchCache` (line 44) stores `Pair<Long, List<ShowCard>>` keyed by `"query::filter"` with a 4-minute TTL, but nothing evicts entries older than 4 minutes except `put` for the same key. The number of distinct queries a heavy user types in a session is small (tens), so memory impact is minor — but the same is true of `episodesCache` (line 117) storing full `ShowDetails` (episode lists + poster URLs) keyed per show URL: opening 30 show drawers in a session keeps 30 full page parses in memory. Both are bounded by usage, not by a cap. On a low-RAM phone this is a few MB at most — acceptable, but the "cache" also has a behavioral quirk: a cache hit (line 52) still re-runs the entire multi-site search, so the 4-minute cache saves UI latency, not bandwidth — every keystroke search still fans out to all 11 providers plus dynamic ones.

- **[major] `data/net/HttpClient.kt:83-132` — the DoH cache never expires.** `dohCache` (line 83) stores DoH-resolved addresses for hostnames that failed system DNS, and entries are never removed or time-stamped. A hostname that is temporarily unresolvable (ISP DNS hiccup, site's DNS flapping) gets cached and then served stale for the rest of the process — if the site changes its A records, the app keeps connecting to the dead IP until app restart. Real impact: a site that "comes back" after DNS changes remains unreachable until the user force-stops the app. The comment says the cache exists to "avoid redundant HTTPS lookups" — for a handful of hostnames, an unbounded never-expiring cache is the wrong trade.

- **[major] `engine/DownloadEngine.kt:1185-1219 + 1243-1272` — the watchdog heuristics are hostile to legitimately slow-but-alive transfers.** The crawl floor (64 KiB / 60s ≈ 1 KiB/s, line 531-532) and the rate-drop detector (line 1219-1220: best burst ≥ 1 MiB/s, then a 30s window below 40% of best → kill) are tuned against throttling CDNs (documented vidsrc behavior), but they will also fire on: (a) genuine 2G/edge connections — a transfer averaging 800 B/s that never reaches 64 KiB in 60s is stall-killed even though it is progressing; the "resets on any progress" rule at line 1198 only resets `stallKills`, and only when `bestWindowBps < 1 MiB/s` — a task that once hit 1.2 MiB/s in a burst and then genuinely slows (radio handover, another app's traffic) is killed repeatedly; (b) small files on slow networks, where 8 stall kills (MAX_STALL_KILLS, line 537) × 60s ≈ 8 minutes of kill/relaunch cycles before FAILED — each kill forces a backend restart and, for the yt-dlp path, a full re-resolve (fresh token) which costs more requests. The design intent is defensible (a dead CDN must not pin a task forever), but there is no distinction between "server throttled" and "user network is slow", and the phone-side cost of the recovery chain (re-resolve + retries) is charged to the user's data plan on every kill.

- **[major] `engine/TurboDownloader.kt:158` + `engine/DownloadEngine.kt:35-36` — `parallelSocketsPerFile = 16` with `maxConcurrentDownloads = 3` means up to 48 simultaneous TCP connections plus resolver traffic on a phone radio.** Sixteen parallel sockets to a single host is standard for aria2c-style saturating on fixed broadband, but on a mobile radio (LTE/4G carrier, and especially the Nigerian ISP networks this app explicitly targets — see the DoH fallback comment at HttpClient.kt:96) 16 sockets per file provides diminishing returns: the bottleneck is the radio link, not the TCP window, and each connection carries per-connection TCP/IP overhead plus retransmission amplification on lossy links. Three concurrent tasks at 16 sockets each can also trip `maxRequestsPerHost = 32` (HttpClient.kt:19) when two tasks hit the same CDN, silently reducing one task's concurrency. Worth a per-network cap (e.g., metered → 4 sockets) rather than a blanket 16.

## Minor

- **[minor] `engine/DownloadEngine.kt:402-430` — `computeDiskBytes` runs every 2 seconds per active task and does `dir.listFiles()` + per-file `length()` + a full `TurboState` sidecar read.** For a torrent with a large file this is a directory scan and a multi-line sidecar parse (one line per 1 MiB piece — a 4 GB file = 4096 lines) every 2s per task. With 3 concurrent tasks that is 3 directory scans + 3 full sidecar parses per 2s window. The watchdog's 2s cadence (line 1146) is fixed and cannot be relaxed for large torrents; on low-end devices with slow flash this adds measurable CPU/I/O churn for the entire download duration, and it competes with the IO-thread contention described in the critical finding.

- **[minor] `engine/DownloadEngine.kt:1213-1214` — the zombie cap for magnets is `STALL_TIMEOUT_MS * 20` (20 minutes).** A magnet with a dead swarm holds a DOWNLOADING slot — and one of the `maxConcurrentDownloads = 3` — for up to 20 minutes while the user's other queued downloads wait. The 20× multiplier was a deliberate fix for slow DHT bootstrap (comment at lines 1207-1211), but the engine does not bound the total swarm-wait by the user's stall setting; a user who lowered stallTimeoutSec to 30 still gets 10 minutes of zombie magnet time. The magnet is exempted from the crawl/stall kill entirely (`if (!magnetTask && ...)` at line 1243), so only the zombie cap ends it.

- **[minor] `engine/HlsSizeEstimator.kt:107-111` — the audio-rendition probe reuses the video's `fmp4` flag.** `estimateFromSamples(listOf(audioSample), audioCount, fmp4)` applies the video-segment remux factor (0.93 or 0.99) to audio segments, whose wire format (AAC/AC3) has a different remux overhead. Audio is a small fraction of total size, so the error is small, but the flag is semantically wrong.

- **[minor] `engine/HlsSizeEstimator.kt:132-151` — `probeSegmentSize` parses `Content-Range` with `substringAfter('/')`.** If a CDN returns a nonstandard `Content-Range` (e.g., `bytes */1048576` for an unsatisfiable range, or with leading spaces), the parse returns null and the whole estimate collapses to `null` — the estimator is a "one bad probe = no estimate" design (line 89). For a diagnostic feature, a robust total-size fallback (e.g., from `Content-Length` on a non-range response, which is already handled for 200) would keep the estimate alive across more CDN quirks.

- **[minor] `resolvers/Resolvers.kt:183-194` — `resolveWithRetry` uses a fixed 1500ms delay, not exponential backoff.** Three network-class failures cost 3 seconds of wall time plus the round-trips; on a genuinely flaky connection the whole 25-resolver registry walk re-runs the same failed host's resolver 3 times before giving up. Monolith parity justifies the structure, but the fixed delay is easy to improve (e.g., 1.5s / 4s / 9s).

- **[minor] `engine/DownloadEngine.kt:1621-1627` — rewritten HLS masters are only cleaned up on the yt-dlp success/failure path.** If the task is paused or cancelled mid-preflight (CancellationException before line 1621), the `hls-<taskId>*.m3u8` scratch files stay in `context.cacheDir/hls` until the OS evicts the cache directory. Each rewrite is small (KB), but repeated pause/retry cycles accumulate files, and the cleanup code is duplicated in spirit with `preflightHls`'s own `created` list which is only deleted on the probe-failure branch (lines 878-881).

- **[minor] `pipeline/HostHealth.kt:114-124` — the backoff window (30s..1h exponential) gates hosts at depth 0 only.** `ResolverRegistry.resolve` checks `HostHealth.isUsable` only at `depth == 0` (Resolvers.kt:71); every nested `resolve(url, quality, depth+1)` call inside resolvers (Vidbasic line 245, KisskhMegaplay line 373, the engine's own line 724) bypasses the gate. A host in a 1-hour backoff window can still be hammered by recursive descent — e.g., a gateway page that embeds 5 dead-locker iframes will fire 5 fetches at a backoff host. This directly undermines the "no request to dead hosts" data discipline the ledger exists to enforce.

## Nits

- **[nit] `engine/TurboDownloader.kt:296-302` — `claimNext()` busy-waits on the atomic `nextPiece` counter.** When all workers have completed every piece, `claimNext()` keeps looping (`while (true) { ... }`) until `idx >= plan.size`. For a download finishing with fewer workers than pieces this is a tiny spin, but it's a classic busy-loop pattern that will burn CPU if `plan.size` is small and workers are many (plan is capped at `sockets * 8`, so at most a few wasted spins — negligible).

- **[nit] `providers/ProviderRegistry.kt:52-54` — cache-hit search still emits twice.** A cached search sends the stale list instantly, then re-runs the full multi-site crawl and sends the fresh list; the UI briefly shows stale results then updates. This is intentional stale-while-revalidate, but combined with the 4-minute TTL it means the cache does not save bandwidth at all — it only makes the first frame fast. If bandwidth is the goal, a hard cache hit (no re-crawl) for, say, 60s would be the cheaper default.

- **[nit] `data/net/HttpClient.kt:41-55` — cookie store eviction drops the OLDEST cookie by insertion order, not by expiry.** `while (cookies.size > MAX_COOKIES) cookies.removeAt(0)` evicts the least-recently-added cookie even if it is still valid, while an already-expired cookie stays until `loadForRequest` prunes it. On a long session that reaches 400 cookies, a still-valid session cookie for the currently-resolving locker can be evicted mid-handshake. Impact is theoretical (400 cookies is a lot for a handful of locker hosts), but expiry-aware eviction is a one-line fix.

## Verdict

The concurrency design is mostly right — bounded races, depth caps, request-body caps (`MAX_TEXT_BYTES`), a bound on the cookie jar, TTL'd resolve cache, and a genuine effort to kill work on pause — but the two biggest costs on mobile are structural: blocking OkHttp calls on the shared IO dispatcher (48+ threads pinned by 3 downloads) and cross-task cancellation through the global `cancelInFlight`, both of which turn a multi-download phone session into a thundering herd on a 64-thread pool and a data-plan liability. The per-episode request fan-out (up to 3 raced candidates, each with recursive descent through 25 resolvers, plus multi-variant HLS preflight, doubled on every token refresh) is bounded but heavy on slow networks, and the estimator's 4-sample mean is too crude to be fed into the user-visible progress total. The watchdog's stall/crawl/rate-drop heuristics are well-documented and defensible for their target (throttling CDNs), but they have no way to distinguish a throttled server from a slow radio, and the 8-kill recovery chain spends real bandwidth re-resolving before failing. Overall: thoughtful resource discipline at the edges (caps, TTLs, monotonic progress), undermined at the center by shared mutable globals and blocking I/O on the IO pool.
